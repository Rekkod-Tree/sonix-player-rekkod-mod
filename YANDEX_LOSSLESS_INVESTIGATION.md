# Яндекс: запрошен Lossless, получен AAC

Статус: расхождение подтверждено и историческими журналами, и контрольными
запросами с текущей сессией подключённого R1. Причина не установлена,
исправление не заявляется. Для следующего шага требуется сравнение с
официальным приложением под тем же аккаунтом на одной записи.
Звуковые настройки, пресеты и воспроизведение не изменялись.

## Наблюдение пользователя

За время использования он не видел полученного FLAC Яндекса. Для последующих
сравнений звука подтверждён именно **Space One Pro - Body Voice test**, а не
его вариант Natural. Параметры существующего пресета сохранены без изменений.

## Что показали журналы

Прочитаны только отобранные строки о формате/транспорте и флаг Plus;
токены, ключи, подписанные URL и содержимое аккаунта не выводились.

| Аппаратный сеанс | Записей результата | Запрошено | Ответ сервиса |
| --- | ---: | --- | --- |
| Alpha20, обучение PGO | 7 | lossless, encraw | aac-mp4, 192 кбит/с, nq, encraw |
| Alpha20, конечная программа | 2 | lossless, encraw | aac-mp4, 192 кбит/с, nq, encraw |

Это девять записей запросов, не утверждение о девяти разных композициях.
В обоих журналах зафиксировано `account has Plus: yes`. В этих результатах
не обнаружены сообщения о запасном переходе encraw → raw из-за отказа/ключа.
Следовательно, ни отсутствие Plus, ни такой переход не подтверждаются
как объяснение именно этих записей. Наличие Plus не устанавливает все права
конкретной сессии, региона или записи.

Историческая копия настройки из установленной Alpha20 тоже содержит
`[yandex] quality=lossless`; это не чтение текущей конфигурации устройства.

Источники в рабочей папке Mediateka, не публикуемые целиком:

- `output/alpha20-runtime-generate/candidate-training.log`
- `output/alpha20-runtime-use-trained/candidate-final.log`
- `output/alpha20-installed-audit-20261018/before-config-private.ini`

## Что делает наш код

`yandex_get_quality()` по умолчанию выбирает lossless. В `yandex_file_info()`
сначала запрашиваются FLAC/flac-mp4 и другие кодеки через encraw. Фактический
ответ отдельно записывается через `note_format()`. После трёх определённых
отказов encraw возможен выбор raw до перезапуска, но это не наблюдалось
в рассмотренных записях.

Фраза журнала «has no lossless file for this account» — трактовка клиента
после ответа в другом кодеке, а не независимое доказательство отсутствия
версии FLAC в каталоге. Её нельзя использовать как установленную причину.

## Что нужно сопоставить дальше

1. Текущую настройку качества, версию и свежий ответ на один известный трек.
2. Подтверждённую доступность Lossless того же трека в официальном клиенте
   для того же аккаунта; наличие обычного Plus само по себе недостаточно.
3. Параметры запроса и профиль клиента, доступные данной сессии права.
   Запрос только FLAC нужен как диагностическая проба, не как автоматическая
   замена обычного воспроизведения с запасным форматом.
4. Полученный кодек, качество и транспорт до кеширования и то, что отображает
   плеер. Проверку токена или заголовков нельзя заменять выводом их значений
   в общий журнал.

## Контроль с подключённым устройством

Подключён `ingenic_`, установлена Alpha20, сборка 181020260707. Текущая
настройка Яндекса — lossless, активный пресет — Space One Pro - Body Voice test.
В интерфейс команды не отправлялись, аудио не скачивалось, сессия не обновлялась.

Существующий access token прочитан в память для ограниченных HTTPS-запросов
к API Яндекса с компьютера. Авторизация не передавалась другим сайтам;
токен, ключи файлов и подписанные URL не сохранены в результаты. Это не
повторный запуск аудиотракта на R1 и не проверка его сетевого маршрута.

Проверен опубликованный профиль Desktop открытого клиента MarshalX. Его
константы разобраны как данные, без исполнения скачанного Python-кода;
сохранён SHA-256 источника, но не ключи. Этот тест не доказывает идентичность
содержимого запечатанных ключей конкретной прошивки.

- Текущий `account/status`: HTTP 200, Plus есть, сервис доступен; в разрешениях
  присутствуют high-quality и play-full-tracks. Простой вывод об отсутствии
  подписки этими данными не подтверждается.
- На записи из аппаратного прогона запрос lossless/encraw вернул AAC 192/nq.
  Ограничение списка только FLAC/flac-mp4 вернуло MP3 192/nq; raw вернул AAC
  192/nq. Все ответы HTTP 200.
- На публичной контрольной записи из исторического примера библиотеки
  получены такие же три ответа. Пример не доказывает текущей доступности
  FLAC этой записи в официальном приложении.
- На первой записи запрос hq вернул AAC 192/nq; старый download-info сообщил
  только MP3 192, без preview.
- Найден официальный плейлист yandexmusic, kind 1383, «Прислушайтесь к Lossless»,
  63 записи. Два первых трека при lossless/encraw тоже вернулись как AAC 192/nq.
  Это контроль по заявленной подборке, не подтверждение текущей индикации
  конкретной записи в приложении пользователя.

Сужение причины: ответ получается до кеширования, декодирования и показа UI.
Но ошибка интеграции/профиля авторизации всё ещё возможна: повторение ответа
с тем же токеном в другом клиенте не оправдывает способ выдачи этого токена.
Пока нельзя ни гарантировать получение FLAC, ни объявить неисправным аккаунт,
ни рекомендовать покупку другой подписки. Нужен тот же трек в официальном
приложении; пользователь об этом спрошен.

## Диагностический хелпер

`tools/yandex-audit/probe_lossless.py` делает один запрос статуса и до трёх
запросов формата для указанного ID. Не обновляет токен, не загружает аудио,
не пишет на плеер и не управляет UI. Перенаправления запрещены, ошибки
авторизации/ограничения частоты прекращают оставшиеся варианты. Нужен
собственный подключённый R1 с действующей сессией; секреты в аргументах
командной строки не передаются.

```text
python tools/yandex-audit/probe_lossless.py --adb C:\platform-tools\adb.exe --track TRACK_ID --output report.json
python -m unittest discover -s tools/yandex-audit -p test_probe_lossless.py -v
```

Пять офлайн-проверок прошли: отсутствие личных полей/секретов/ссылок в сводке,
остановка после отказа или 429, запрет посторонних endpoint, запрет redirect,
чтение токена через совместимый со старым adbd shell. Первая попытка через
exec-out на данном adbd не сработала; исправлен именно диагностический
хелпер. Это не исправление загрузки FLAC в прошивке.

Для сравнения изучена текущая реализация
[MarshalX/yandex-music-api](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client/tracks.py):
`tracks_file_info` отдельно задаёт профиль Desktop для этого запроса; сервер
сам выбирает доступный кодек. Это полезная контрольная реализация, но её
параметры не доказывают причину нашего ответа и не должны копироваться
вслепую без сопоставления запросов.

**Граница вывода:** в коде есть запрос FLAC, но сохранённая аппаратная проверка
Яндекса подтвердила AAC, а не FLAC. Работоспособность получения FLAC на данной
сессии ещё требуется доказать. Источник не переименовывается в FLAC и не
перекодируется в FLAC для создания ложной индикации Lossless.
